【一、它能做什么】

  打开 B 站视频页时，右下角会出现一个下载面板：
    · 列出这个视频真实可用的画质 / 音质档位，由你自己挑
    · 三种下载方式：音频（.m4a 或 .mp3）、仅视频、视频+音频（自动合并成单个 MP4）
    · 音频可转成 mp3：纯前端转码，不需要 ffmpeg，也不联网
    · 支持暂停 / 继续 / 取消
    · 自动识别当前正在播放的分P（多P视频不用手填）

  和普通嗅探插件的区别：它不是猜一个最高清晰度就去下，
  而是把接口返回的档位全列出来（同一档位还会按 H.264 / HEVC / AV1 分开），
  你可以为兼容性选 H.264，也可以为省流量选 AV1。


【二、安装】

  1. 打开 chrome://extensions
     （Edge 用 edge://extensions，操作一样）

  2. 打开右上角的「开发者模式」

  3. 点「加载已解压的扩展程序」，选中本文件夹（bili-downloader）

  4. 打开任意 B 站视频页，右下角应出现下载面板

  以后改了代码：回到 chrome://extensions 点扩展卡片上的「重新加载」，
  再刷新 B 站页面即可生效。


【三、界面说明】

  ┌──────────────────────────┐
  │ 画质  [1080P · H.264 · 1.9M]   │  ← 下拉选择视频档位
  │ 音质  [192K · AAC · 192kbps]   │  ← 下拉选择音频档位
  │ 格式  [m4a / mp3]              │  ← 音频格式，只影响「🎵 音频」
  │ [↻ 读取可选档位]                │  ← 手动刷新档位列表
  ├──────────────────────────┤
  │ [🎵 音频]                       │  ← 只下音轨（.m4a）
  │ [🎬 仅视频]                     │  ← 只下画面（.mp4）
  │ [🎬🎵 视频+音频]                │  ← 自动合并成单个 MP4
  ├──────────────────────────┤
  │ [⏸ 暂停]      [✕ 取消]         │  ← 下载中才可用，空闲时是灰的
  │            ▲                  │  ← 点它收起/展开整个面板
  └──────────────────────────┘

  档位列表：进页面约 2 秒后自动读取一次，不用手点。
            同一分P只会读一次，不会因为刷新页面而重置你的选择。
            没读到就点「↻ 读取可选档位」。
            点 ↻ 时如果某档拿不到，还会弹窗告诉你原因。

  档位选择会被记住（存在本地），下次打开同类型的视频仍然有效；
  如果某个视频没有你选的那一档，会自动退回「最高（自动）」。


【四、怎么用】

  1. 打开视频页，等右下角档位列表自动填好

  2. （可选）在画质/音质下拉里选想要的档位
     不选就按「最高（自动）」——它按「档位优先、同档挑码率最高」来选

  3. （可选）在「音频格式」下拉里选 m4a 或 mp3
     （这个选项只影响「🎵 音频」按钮，见下方说明）

  4. 点「🎬🎵 视频+音频」
     → 按钮会依次显示「解析中…」「下载中 xx%」「合并中」
     → 完成后弹窗告诉你文件在哪、多大多清晰

  5. 中途想停：点「⏸ 暂停」（变成「▶ 继续」），或点「✕ 取消」

  一次只能跑一个下载任务，下载期间三个下载按钮都会被禁用。


  ── 关于音频格式 ──

  面板上的「音频格式」只影响「🎵 音频」这个按钮：

    m4a  直接把 B 站的原始音轨存下来：最快，音质与网页播放完全一致（默认）
    mp3  转成 192kbps 的 mp3。自动在两条路里挑，你什么都不用设置：

         · 本机装了 FFmpeg（见 native-host\INSTRUCTION.txt）
           → 交给 FFmpeg 转：快得多，页面也完全不占内存。
             装好宿主后，这里和「视频+音频」的合并都会自动走它。

         · 没装 → 浏览器里自己转：
           Web Audio 把 m4a（AAC）解码成 PCM，再用 lamejs（纯 JS）编码成 mp3。
           不需要 ffmpeg、不需要 wasm、也不联网；
           长音频要等几秒到几十秒，期间按钮显示「转码 xx%」。

  注意：合并下载（🎬🎵 视频+音频）始终使用原始 m4a，不受这个选项影响。
        内置转码依赖浏览器自带的 AAC 解码器；万一解码失败会有明确提示，
        把「音频格式」改回 m4a 即可正常下载。
        若本地 FFmpeg 转码中途失败（例如那份构建不带 mp3 编码器），
        也会自动退回内置编码器，不会让你白等。

【六、文件命名与保存位置】

  文件名规则：
      视频标题[_分P名][_p分P号].后缀

  · 分P名和 P 号只在多P视频里才拼进去；单P视频直接就是「主标题.后缀」
  · 不再拼接 audio / video / merged 之类的类型后缀

  例子：
      单P视频  某视频.mp4                 某视频.m4a
      多P视频  某视频_第3话_p3.mp4         某视频_第3话_p3.m4a

  三种下载对应的后缀：
      音频            → .m4a
      仅视频          → .mp4
      视频+音频       → .mp4

  说明：同一支视频如果先下了「仅视频」再下「视频+音频」，两个文件名会一样，
  浏览器会自动存成「某视频 (1).mp4」，不会互相覆盖。

  唯一的例外是第 7 节的「通道 C 兜底」：那条路要分别下视频和音频让你手动合并，
  合并结果会命名为「某视频_第3话_p3 完整版.mp4」—— 加「完整版」是为了不和
  它的两个输入文件同名（同名的话 ffmpeg 会直接报错）。

  保存位置：
      · 浏览器内通道   → 浏览器的默认下载目录（可在浏览器设置里改）
      · 原生 FFmpeg 通道 → %USERPROFILE%\Downloads（系统的「下载」文件夹）

  标题里的 Windows 非法字符（\ / : * ? " < > |）会被剔除，
  中文、空格、【】（）等全角符号都会保留，不影响可读性。


【七、三条下载通道（自动切换，不用你操心）】

  合并下载会按下面顺序自动尝试，前一个失败才换下一个：

    通道 A  原生 FFmpeg 宿主
            装了 native-host 才有。输出带 faststart，可边下边播。
            看 native-host\INSTRUCTION.txt 了解安装方法。

    通道 B  浏览器内重封装
            把视频和音频两条 fMP4 的分片直接拼成一个 MP4。
            不解码、不转码，毫秒级完成，画质音质零损失。
            所以即使没装 FFmpeg，普通视频也能拿到单个 MP4。

    通道 C  兜底：分别下载视频和音频两个文件，
            并弹窗给你一条 FFmpeg 命令行让你自己合。

  下载单条流时也有兜底：页面直连失败会自动改用后台通道，
  并且会依次尝试 B 站接口一并返回的备用 CDN 地址（有几个试几个）。


【八、常见问题】

  Q：画质只有 480P？
     A：未登录。B 站对未登录账号最高只给 480P。
        登录后能拿到 1080P，大会员才能拿到 4K / 8K / HDR / 杜比视界。
        控制台会打印 [bili-dl] 账号状态：... 可以直接看当前状态。

  Q：选不到 4K / 8K / HDR？
     A：需要大会员。另外杜比视界（126）在普通播放器上可能偏色，
        介意的话改选 4K 或 HDR。

  Q：检测不到 Hi-Res 无损音质？
     A：这不是插件的问题。已实测确认：该音轨属于 APP 端功能，
        网页接口不下发 —— 换参数、甚至照抄网页播放器自己发的那条请求，
        拿到的 flac.audio 都是 null。
        网页端能拿到的最高音质是杜比全景声（若该视频有）或 192K AAC。

  Q：下载出来 0 字节 / 一直失败？
     A：B 站 CDN 的防盗链。扩展会自动改用后台通道重试，
        也会自动换备用 CDN 地址。若都不行，可能是该视频有额外限制。

  Q：合并出来的 MP4 播放器打不开，或者只有声音没画面？
     A：多半是选了 AV1 / HEVC 而播放器不支持。
        在相同位置把画质改选成 H.264 的同一档，重新下载即可。
        （Windows 自带播放器对 AV1/HEVC 支持有限，推荐 VLC / mpv / PotPlayer）

  Q：暂停之后进度条不动了，是卡死了吗？
     A：不是，暂停就是真的停住读取（实测进度会完全静止），
        点「▶ 继续」会立刻接着跑。
        注意别暂停太久 —— 时间长了 CDN 可能把连接断掉，建议几分钟内恢复。

  Q：面板挡住视频了 / 想关掉？
     A：点最下面的「▲」收起，档位菜单和按钮会一起折叠。
        位置固定在右下角，不会跟着页面滚动跑。

  Q：换了分P之后档位没更新？
     A：切分P后会自动重新读取（B 站是单页应用，切P不刷新页面，
        扩展监听了地址变化）。没更新就点一下 ↻。


  Q：下载完成了，却没看到提示弹窗？
    A：这个页面被放进了沙箱 iframe，浏览器会禁止这种页面弹窗
       （控制台会报 "The document is sandboxed, and the 'allow-modals' keyword is not set"）。
       这种情况扩展会自动改成右下角浮层提示（点一下可关掉），文件本身已经下载好了。


  Q：控制台报 "Download is disallowed. The frame initiating or
     instantiating the download is sandboxed, but the flag
     'allow-downloads' is not set"？
    A：同一个沙箱 iframe 会把「保存文件」这个动作一起拦掉 ——
       页面里创建的 <a download> 点击会被浏览器直接拒绝。
       现在保存改走扩展自己的下载接口（chrome.downloads），
       不受页面沙箱约束，被拦也不会丢文件。
       这条红字若仍出现，说明页面内的兜底路径被走过一次，
       文件实际已由扩展落盘 —— 以「下载」里有没有文件为准。


  Q：下载下来的文件没有后缀，或者名字变成了「下载」？
    A：这是 v1.17.2 的缺陷，现已修好。
       起因：当下载地址是 data: 时，Chrome 的下载接口会完全忽略
       程序给的文件名，落盘时改用系统默认名（中文环境就是「下载」），
       后缀也一起丢了 —— 文件内容其实是完整的。
       现在的做法：落盘时由扩展注册的文件名纠正监听器
       （chrome.downloads.onDeterminingFilename）把名字与后缀改写回来，
       并按扩展名补正数据的 MIME 类型。
       附注：v1.17.3 曾试过「让扩展直接下载原始地址」，实测 B 站 CDN
       会拒绝扩展发起的下载（主地址与备用地址全部失败），而且每次都在
       浏览器下载列表里留下几条「无法从网站上提取文件」的失败记录，
       该路径已在 v1.17.4 移除。
       若仍看到「下载」这类名字，请确认扩展已重新加载：
       控制台第一行应打印 [bili-dl] 内容脚本已加载 v1.17.4。


【九、权限说明】

  这个扩展申请了下面这些权限，用途如下：

    · 访问 bilibili.com 与视频 CDN
        取流和下载。下载的是你自己在网页上能播放的内容。

    · declarativeNetRequest / declarativeNetRequestWithHostAccess
        B 站 CDN 会校验 Referer 和 Origin。这两个头属于浏览器的
        「禁止修改头」，fetch 里写会被丢弃，必须在请求发出前改写。

    · nativeMessaging
        调用本机 FFmpeg 做合并。属于可选功能 ——
        没装 native-host 就完全用不到，不影响其它功能。

    · downloads
        保存文件。B 站有时把播放器放进沙箱 iframe，页面内的
        <a download> 会被浏览器拒绝；改用扩展的下载接口后，
        落盘不再受页面沙箱限制，文件名也由扩展准确指定。

  注：mp3 转码完全在本地进行，用到的 lamejs 已经打包在扩展里
      （vendor/lamejs.iife.js），不需要任何额外权限，也不会发起网络请求。

    · host_permissions: *://*/*
        用于向 B 站 CDN 取流（CDN 域名是动态的）。
        代码实际只请求 bilibili 相关域名，不会访问其它网站。


【十、日志与排错】

  · 页面控制台（F12）
      所有日志以 [bili-dl] 开头，包括：
        账号状态（是否登录 / 是否大会员 / WBI 密钥）
        接口返回的完整画质、音质档位清单
        每个下载通道的结果、备用地址切换情况

  · 原生宿主日志
      %TEMP%\bilidl_host.log
      （%TEMP% 一般是 C:\Users\你的用户名\AppData\Local\Temp）

  Bilibili Video & Audio Downloader · INSTRUCTION
  Version 1.20.3   Chrome / Edge extension (Manifest V3)

【1. What it does】

  Opening a Bilibili video page brings up a download panel in the bottom-right corner:
    · lists the quality / audio tiers this video really offers, for you to pick from
    · three download modes: audio only (.m4a or .mp3), video only, video + audio (auto-merged into one MP4)
    · audio can be transcoded to mp3 purely in the browser -- no ffmpeg, no network
    · pause / resume / cancel
    · detects the part you are watching (no manual entry for multi-part videos)

  Unlike a typical stream sniffer it does not just guess the highest resolution,
  it lists every tier the API returns (and splits one tier by H.264 / HEVC / AV1),
  so you can pick H.264 for compatibility or AV1 to save bandwidth.


【2. Install】

  1. Open chrome://extensions
        (Edge uses edge://extensions; same steps)

  2. Switch on "Developer mode" in the top-right corner

  3. Click "Load unpacked" and select this folder (bili-downloader)

  4. Open any Bilibili video page -- the panel should appear in the bottom-right corner

  After editing the code: go back to chrome://extensions, click "Reload" on the extension card,
  then refresh the Bilibili page.


【3. The panel】

  ┌──────────────────────────┐
  │ Quality [1080P · H.264 · 1.9M]  │  <- pick the video tier
  │ Audio   [192K · AAC · 192kbps]  │  <- pick the audio tier
  │ Format  [m4a / mp3]            │  <- audio format; affects "audio" only
  │ [↻ refresh tiers]              │  <- refresh the tier list manually
  ├──────────────────────────┤
  │ [🎵 audio]                     │  <- audio only (.m4a)
  │ [🎬 video only]                │  <- video only (.mp4)
  │ [🎬🎵 video + audio]           │  <- auto-merge into one MP4
  ├──────────────────────────┤
  │ [⏸ pause]     [✕ cancel]       │  <- only while downloading; greyed out when idle
  │            ▲                  │  <- collapse / expand the whole panel
  └──────────────────────────┘

  Tier list: fetched automatically about 2 seconds after the page loads; no clicking needed.
            Fetched once per part, so refreshing the page will not reset your choice.
            If nothing shows up, click "↻ refresh tiers".
            When a tier is unavailable, clicking ↻ pops up an explanation of why.

  Your choice is remembered locally and still applies the next time you open a similar video;
  if a video lacks the tier you picked, it falls back to "best (auto)".


【4. Usage】

  1. Open a video page and wait for the tier list to fill in

  2. (Optional) pick the tier you want from the quality / audio dropdowns
        Skip it and "best (auto)" applies: highest tier first, then highest bitrate within that tier

  3. (Optional) pick an audio format (m4a or mp3)
        (this only affects the "🎵 audio" button -- see below)

  4. Click "🎬🎵 video + audio"
        -> the button shows "parsing…", "downloading xx%", then "merging"
        -> a dialog tells you where the file is, its size and its specification

  5. To stop midway: click "⏸ pause" (it becomes "▶ resume") or "✕ cancel"

  Only one download runs at a time; all three download buttons are disabled while it does.


  -- About the audio format --

  The "Format" dropdown only affects the "🎵 audio" button:

    m4a  saves Bilibili's original audio track as-is: fastest, bit-identical to web playback (default)
    mp3  transcodes to 192kbps mp3. It picks between two routes automatically -- nothing to set:

         · A local FFmpeg is installed (see native-host\INSTRUCTION.txt)
           -> hand it over: much faster, and the page holds nothing in memory.
              Once the host is installed, both this and the video+audio merge use it.

         · Not installed -> transcode in the browser:
           Web Audio decodes the m4a (AAC) into PCM, then lamejs (pure JS) encodes mp3.
           No ffmpeg, no wasm, no network;
           long tracks take seconds to tens of seconds and the button shows "transcoding xx%".

  Note: the merge flow (🎬🎵 video + audio) always uses the original m4a and ignores this
        setting. The built-in path relies on the browser's AAC decoder; if decoding fails you
        get an explicit message -- switch the format back to m4a and it downloads fine.
        If a local FFmpeg transcode fails midway (say that build lacks the mp3 encoder) it
        falls back to the built-in encoder automatically, so the wait is never wasted.

       That is why the menu lists "tier + codec" separately, for example:
        「1080P · H.264 · 1.9M」  「1080P · HEVC · 1.4M」  「1080P · AV1 · 1.1M」
       Which to pick: H.264 for compatibility; HEVC or AV1 to save bandwidth and disk space.


【6. Filenames and save location】

  Filename pattern:
      video title[_part name][_p<part number>].<ext>

  · The part name and the P number are only included for multi-part videos;
    a single-part video is simply "main title.<ext>"
  · No audio / video / merged type suffix is appended any more

  Examples:
      single part   Some Show.mp4              Some Show.m4a
      multi part    Some Show_Episode 3_p3.mp4 Some Show_Episode 3_p3.m4a

  Extension by download kind:
      audio            -> .m4a
      video only       -> .mp4
      video + audio    -> .mp4

  Note: if you download "video only" and then "video + audio" for the same video, both
  filenames match and the browser saves the second as "Some Show (1).mp4" -- nothing is
  overwritten.

  The one exception is the channel-C fallback in section 7: that path downloads video and
  audio separately for you to merge by hand, and its merge output is named
  "Some Show_Episode 3_p3 完整版.mp4" (literally "full version"). The marker exists so the
  output does not collide with its own two input files -- ffmpeg refuses to run when the
  output name equals an input name.

  Save location:
      · in-browser channel  -> your browser's default download folder (configurable in browser settings)
      · native FFmpeg channel -> %USERPROFILE%\Downloads (your system Downloads folder)

  Characters Windows forbids (\ / : * ? " < > |) are stripped from titles,
  while CJK, spaces and full-width punctuation such as 【】（） are kept, so titles stay readable.


【7. Three download channels (switched automatically)】

  Merged downloads try these in order, moving on only when one fails:

    Channel A  native FFmpeg host
                      Requires native-host. Output is faststart-enabled, so it plays while downloading.
                      See native-host\INSTRUCTION.txt for the install steps.

    Channel B  in-browser remux
                      Splices the video and audio fMP4 fragments straight into one MP4.
                      No decoding, no re-encoding, done in milliseconds, nothing lost.
                      So even without FFmpeg you still get a single MP4 for ordinary videos.

    Channel C  last resort: downloads video and audio as two files
                      and pops up an FFmpeg command line for you to merge them yourself.

  Single streams fall back too: if the direct page fetch fails it switches to the background channel,
  and it tries every backup CDN address the API returned alongside (as many as there are).


【8. FAQ】

  Q: Only 480P available?
     A: You are not logged in. Bilibili caps anonymous accounts at 480P.
            Logged in you get 1080P; 4K / 8K / HDR / Dolby Vision need a premium membership.
            The console prints "[bili-dl] account state: …" so you can check at a glance.

  Q: Cannot get 4K / 8K / HDR?
     A: They require a premium membership. Note Dolby Vision (126) can shift colours on plain players,
            so pick 4K or HDR instead if that bothers you.

  Q: Hi-Res lossless audio never shows up?
     A: That is not an extension bug. Measured: the track is an app-only feature and the
            web API never serves it -- changing parameters, or even replaying the web player's own request
            verbatim, still returns flac.audio = null.
            The best the web side offers is Dolby Atmos (when the video has it) or 192K AAC.

  Q: Zero bytes / keeps failing?
     A: CDN hotlink protection. The extension retries through the background channel automatically
            and switches to backup CDN addresses. If all fail the video may carry extra restrictions.

  Q: The merged MP4 will not open, or has sound but no picture?
     A: You most likely picked AV1 / HEVC and your player does not support it.
            Re-download the same tier with H.264 selected instead.
            (Windows' built-in player has limited AV1/HEVC support; VLC / mpv / PotPlayer are recommended.)

  Q: The progress froze after pausing -- is it stuck?
     A: No. Pausing really does stop the reads (progress stays completely still in testing);
            clicking "▶ resume" picks straight back up.
            Do not pause for too long though -- the CDN may drop the connection; a few minutes is safe.

  Q: The panel covers the video -- how do I hide it?
     A: Click the "▲" at the bottom; the tier menus and buttons collapse together.
            It stays pinned to the bottom-right and never scrolls away.

  Q: Switching parts did not refresh the tiers?
     A: It re-fetches on a part switch (Bilibili is a SPA, so switching parts does not reload the page;
            the extension watches the URL). If nothing changes, click ↻.


  Q: The download finished but no dialog appeared?
    A: This page sits inside a sandboxed iframe, and browsers block dialogs there
       (the console says "The document is sandboxed, and the 'allow-modals' keyword is not set").
       The extension falls back to a toast in the bottom-right corner (click to dismiss);
       the file itself is already downloaded.


  Q: The console says "Download is disallowed. The frame initiating or
     instantiating the download is sandboxed, but the flag
     'allow-downloads' is not set"?
    A: The same sandboxed iframe also blocks the save step itself -- an in-page
       <a download> click is refused outright by the browser. The save now goes
       through the extension's own download API (chrome.downloads), which the page
       sandbox cannot reach, so a blocked page no longer loses the file. If the red
       line still appears, the in-page fallback ran once; the file was written by the
       extension API -- trust your Downloads list.


  Q: The downloaded file has no extension, or is named "download"?
    A: A v1.17.2 defect, now fixed.
       Cause: when the download URL is a data: URL, Chrome's download API ignores
       the programmatic filename completely and falls back to the system default
       name (localized, hence "download"), dropping the extension with it -- the
       file contents are fine.
       What happens now: a filename-correcting listener registered by the extension
       (chrome.downloads.onDeterminingFilename) rewrites the correct name and
       extension at save time, and the payload is retyped to match its extension.
       Footnote: v1.17.3 briefly tried having the extension download the original
       URL directly; the Bilibili CDN rejected extension-initiated downloads
       (primary and backup URLs alike) and every attempt left several "failed to
       extract file from the website" rows in the browser's download list, so that
       route was removed in v1.17.4.
       If you still see a name like "download", make sure the extension was
       reloaded: the first console line should read
       [bili-dl] content script loaded v1.17.4.


【9. Permissions】

  The extension requests the following permissions, for these reasons:

    · Access to bilibili.com and the video CDNs
          Fetching and downloading. What you download is what you can already play in the page.

    · declarativeNetRequest / declarativeNetRequestWithHostAccess
          The Bilibili CDN checks Referer and Origin. Both are forbidden header names,
          so setting them in fetch is dropped -- they must be rewritten before the request leaves.

    · nativeMessaging
          Calls your local FFmpeg to merge. Optional --
          without native-host installed it is never used, and nothing else is affected.

    · downloads
          Saving files. Bilibili sometimes puts the player in a sandboxed iframe where
          an in-page <a download> is refused by the browser; going through the
          extension download API lifts the save out of the page sandbox and pins down
          the filename exactly.

  Note: mp3 transcoding happens entirely locally. The lamejs encoder it uses ships inside
        the extension (vendor/lamejs.iife.js); it needs no extra permission and makes no
        network requests.

    · host_permissions: *://*/*
          Used to fetch streams from the Bilibili CDNs (whose hostnames are dynamic).
          The code only ever requests bilibili-related hosts and touches no other site.
